## 1. Авария: сайт лежал, диск был забит на 100%

**Что случилось.** При пересборке контейнера диск ушёл в ноль. MySQL встал:
запросы висели в `waiting for handler commit` по 440 секунд, сайт не отвечал.
Причина — docker build cache разросся до 5.9 ГБ и сборка добила последние байты.

**Что сделано.** `docker builder prune -af` → освободилось 5.9 ГБ, сайт поднялся,
MySQL разгрёб очередь.

**Итог по диску за сессию:** было 99% (947 МБ свободно) → стало **91% (5.2 ГБ)**.

| Что | Освобождено |
|---|---|
| Docker build cache | 3.93 ГБ |
| `/var/log` (fail2ban.log 459 МБ + syslog 115 МБ) | 653 МБ |
| Бэкапы GML от 27 июля (4 файла) | 133 МБ |

Удалённые бэкапы: `data.db.backup`, `data.db.bak-20260727-174528`,
`data.db.before-restart-1738`, `data.db.pre-hwidfix`. Перед удалением живая
`data.db` проверена: `integrity_check: ok`, 5 таблиц. После `truncate` демоны
продолжают писать (проверено замером за 45с) — логирование не потеряно.

## 2. Причина падений Next.js — найдена и устранена

**Симптом.** `uncaughtException: Invalid state: ReadableStream is already closed`,
воркер отваливался, игроки ловили 502.

**Корень.** `app/api/launcher/download/route.ts:31` отдавал Node-стрим через
ложный каст. `as unknown as` — это ложь компилятору: Node-стрим не является
web-`ReadableStream`. Работало, пока клиент дочитывал файл до конца. Но лаунчер —
8 МБ по плохому каналу, и когда игрок обрывал загрузку, undici пытался закрыть
уже закрытый стрим → исключение в обход роута.

```ts
- const stream = fs.createReadStream(absolute)
- return new Response(stream as unknown as ReadableStream, {
+ const stream = Readable.toWeb(fs.createReadStream(absolute)) as ReadableStream
+ return new Response(stream, {
```

**Проверено:** скачивание отдаёт 8201869 байт — байт-в-байт с БД, валидный NSIS.
10 оборванных загрузок (обрыв на 150мс + range-запросы) → **ноль крэшей**,
`RestartCount=0`. До фикса такой обрыв ронял воркер.

**Важное уточнение.** Те 502, что я раньше списал на крэши, оказались от моего же
рестарта в 21:22:41. Реальный крэш был один, в 21:21:04, и `instrumentation.ts`
его перехватил — процесс выжил. Crash-handler работал, но глушил симптом; теперь
устранена причина. Роуты skins/cloak не затронуты — отдают `Uint8Array`.

## 3. Логоспам лаунчера

**Клиент** — `launcher/src-tauri/src/telemetry.rs`: интервал опроса лога 2с → 15с.
Было 30 POST/мин с игрока, стало 4. При 50 онлайн: 1500 → 200 req/мин. Строки не
теряются, едут крупнее пачками; лайв-логи в админке отстают максимум на 15с.

**Сервер** — `app/api/launcher/logs/route.ts`: обрезка окна (`DELETE`) выполнялась
на каждом запросе, хотя удалять почти всегда нечего (хранится 800 строк, пачки по
20–40). Теперь раз в 20 вставок. Убрало ~4-й запрос к БД с каждого POST и работает
независимо от версии лаунчера — то есть защищает и от старых клиентов.

## 5. Что выяснилось про распухание логов

Ротация **не сломана** — logrotate отработал в 00:44, конфиг корректный
(`maxsize 50M`), таймер активен. Файл распух за один день: **~370 МБ за 5 минут,
16:08–16:13**, 137 уникальных IP в одном 8-МБ отрезке. Всплеск распределённой
атаки, fail2ban писал каждую попытку на уровне INFO.

Из 137 IP в срезе забанено было только 13 — тогда nginx-лимиты ещё не стояли.
Сейчас стоят, так что до fail2ban будет доходить меньше мусора.

## ТЗ: что осталось сделать

### Требует решения (отложено по просьбе владельца)

1. **Закоммитить правки.** Три файла: `download/route.ts`, `logs/route.ts`,
   `telemetry.rs`. Typecheck чист, серверная часть в проде и работает.

2. **Релиз лаунчера.** Правка `telemetry.rs` заработает только после сборки с
   Windows-машины через `release-launcher.bat` — на сервере нет Rust-тулчейна.
   До релиза старые лаунчеры продолжат слать раз в 2с (серверный фикс их частично
   компенсирует).

### Рекомендации

3. **`loglevel = NOTICE`** в `/etc/fail2ban/fail2ban.conf` — чтобы INFO-спам
   `Found IP` не засорял диск при следующей атаке. Баны продолжат логироваться.

4. **`docker image prune -af`** — вернёт ещё ~1.21 ГБ. Не критично при 5.2 ГБ.

5. **Следить за диском на открытии.** 59 ГБ всего, из них 5.6 ГБ — `data/`.
   Каждая пересборка съедает место под build cache. Всплеск вроде сегодняшнего
   (370 МБ логов за 5 минут) при малом запасе снова уронит MySQL — уже с игроками.
