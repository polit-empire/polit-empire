# Polit Empire — состояние работ и что делать дальше

Файл-памятка на случай потери сессии при перезагрузке.
Создан: 2026-07-27, ветка `main`.

Кто это писал: сессия Claude Code, работавшая от `claudeuser` (нет sudo, нет доступа
к docker-сокету). Всё, что требует root, выполняет владелец сервера вручную.

## 1. ГЛАВНОЕ: почему VDS зависал и отваливался SSH

**Первопричина — баг DRM-драйвера `cirrus_qemu` в ядре.**

В журнале 438 kernel-warning'ов, все в одном стеке:

```
drm_fb_helper_damage_work -> drm_atomic_helper_dirtyfb -> drm_atomic_commit
  -> drm_atomic_helper_wait_for_vblanks    <- здесь зависает
```

Воркер ждёт vblank, которого на эмулированной видеокарте не бывает, и занимает CPU.
Прямое следствие в логах:

```
clocksource: Long readout interval ... cs_nsec: 11444969980   <- ВМ замерла на 11.4 с
workqueue: drm_fb_helper_damage_work hogged CPU for >10000us 35 times
```

Машина не падает, а **замирает целиком** на секунды. SSH в этот момент не отвечает,
потому что не выполняется вообще ничего. Таких зависаний в логах 19.

За 2026-07-27 было **12 перезагрузок, 7 из них — жёсткие обрывы** без
shutdown-последовательности (боты -1, -2, -4, -5, -6, -7, -11). Логи загрузок -5 и -7
обрываются буквально посреди DRM-стектрейса.

### Что было ИСКЛЮЧЕНО измерением (не тратить на это время повторно)

| Гипотеза          | Проверка                                | Вердикт   |
|-------------------|-----------------------------------------|-----------|
| Нехватка RAM/OOM  | ни одного `oom-kill`, PSI memory = 0    | не оно    |
| Перегрузка хоста  | `steal = 0` в /proc/stat и vmstat       | не оно    |
| Сбой диска        | ни одной `I/O error` в dmesg            | не оно    |
| Сеть/провайдер    | 0 link-флапов, 0 ошибок NIC             | не оно    |
| SSH-брутфорс      | с перезагрузками не коррелирует         | не причина|

### Две поправки к первоначальному (ошибочному) диагнозу

Важно, чтобы никто не повторил эти ошибки:

1. Виснет **`cirrus_qemu`**, а не `simple-framebuffer`. Оба грузятся, но консоль
   в итоге захватывает cirrus: `fbcon: cirrus-qemudrmf (fb0) is primary device`.
2. Сервер грузится через **legacy BIOS**, не UEFI (`/sys/firmware/efi` отсутствует).
   Поэтому `video=efifb:off` здесь **бесполезен** — efifb не используется.
   Нужен именно `nomodeset`.

Ещё нюанс: в `/etc/modprobe.d/blacklist-framebuffer.conf` уже есть `blacklist cirrusfb`,
но это **старый fbdev-драйвер**, а грузится `cirrus_qemu` — другой модуль. Поэтому
существующий блэклист не срабатывал.

### Лечение

Выполнить `deploy/fix-vds.sh` (см. раздел 3), затем `sudo reboot`.

### Краш-луп контейнера `bots` — ИСПРАВЛЕНО

Контейнер падал с `exitCode=1` и был перезапущен **190 раз подряд**.
Причина воспроизведена локально запуском `./venv/bin/python -m bot.main`:

```
RuntimeError: 'cryptography' package is required for
sha256_password or caching_sha2_password auth methods
```

MySQL 8 использует `caching_sha2_password`, а пакета `cryptography` не было в
зависимостях. Отсюда же росли 598 ошибок `[gml-proxy] error: connect ECONNREFUSED
127.0.0.1:5003`.

**Правка:** в `politempire_bots/requirements.txt` добавлен `cryptography>=42.0`.

**Проверено:** после установки пакета бот подключается к БД, проходит миграции и
работает стабильно (падал через ~12 секунд).

**Осталось:** пересобрать образ — это делает шаг 5 скрипта:
```
docker compose build bots && docker compose up -d bots
```

## 3. Скрипт `deploy/fix-vds.sh`

Написан, проверен `bash -n`, sed-выражения протестированы на копиях конфигов,
dry-run прогнан полностью (на копии в /tmp, с обходом проверки root).

```
sudo bash /opt/polit-empire/deploy/fix-vds.sh --dry-run   # посмотреть без изменений
sudo bash /opt/polit-empire/deploy/fix-vds.sh             # применить
sudo reboot                                              # обязательно для шага 1
```

| Шаг | Что делает | Зачем |
|-----|-----------|-------|
| 1 | `nomodeset` в grub + blacklist `cirrus_qemu` + видимое меню GRUB (страховка) | **устраняет зависания и отвал SSH** |
| 2 | Сжатие осиротевших логов, лимит journald 200M, apt clean | освободит ~1.4 ГБ |
| 3 | Починка shebang в `/etc/cron.hourly/logrotate-nginx-size` | заработает ротация по размеру |
| 4 | SSH-хардening + fail2ban (бан 24ч после 3 попыток) | защита от перебора |
| 5 | `docker compose build bots && up -d bots` | конец краш-лупу |

Бэкапы всех изменённых конфигов: `/root/fix-vds-backup-<дата>/`.

### Встроенные защиты

- **Шаг 4 сам себя пропустит, если не найдёт SSH-ключей** — иначе при закрытом
  пароле и отсутствии ключа можно потерять доступ к серверу. На момент написания
  ключей не было, поэтому root-логин останется на пароле (защиту держит fail2ban).
  Чтобы закрыть по-настоящему: `ssh-copy-id root@85.192.56.40`, затем перезапустить скрипт.
- `docker system prune` **НЕ выполняется** — скрипт только показывает `docker system df`.
  Prune необратимо удаляет образы и тома, запускать вслепую нельзя.

### Восстановление, если что-то пошло не так

Скрипт делает меню GRUB видимым (`GRUB_TIMEOUT=5`, `GRUB_TIMEOUT_STYLE=menu`,
`GRUB_TERMINAL=console`) — до этого стояло `GRUB_TIMEOUT=0` + `hidden`, и запасное
ядро можно было выбрать только вслепую поймав Shift через VNC.

1. **Обычно SSH просто работает** (`nomodeset` трогает только графику, не сеть):
   ```
   sudo cp /root/fix-vds-backup-*/grub /etc/default/grub
   sudo update-grub && sudo reboot
   ```
2. **Если SSH не отвечает** — VNC/консоль в панели хостера, те же команды.
   Картинка будет текстовой, низкого разрешения — это нормально при nomodeset.
3. **Если не грузится вообще** — в меню GRUB (висит 5 секунд) выбрать
   `Advanced options` -> ядро **7.0.0-27-generic** (установлено рядом с `-28`),
   загрузиться и откатить командами из п.1.

**Полный откат всего скрипта:**
```
sudo cp /root/fix-vds-backup-*/grub          /etc/default/grub
sudo cp /root/fix-vds-backup-*/journald.conf /etc/systemd/journald.conf
sudo cp /root/fix-vds-backup-*/fail2ban      /etc/logrotate.d/fail2ban
sudo rm -f /etc/modprobe.d/blacklist-cirrus-qemu.conf
sudo rm -f /etc/fail2ban/jail.d/politempire-sshd.local
sudo update-grub && sudo reboot
```
Необратимо только сжатие старых логов nginx в `.zst` (читаются через `zstdcat`).

## 4. Найдено попутно (о чём владелец не знал)

### Ротация логов nginx сломана двумя независимыми способами

1. **Осиротевшие несжатые файлы:** `error.log-20260727` (779 МБ) и
   `access.log-20260727` (466 МБ) — при том что соседние за 23–26 июля сжаты в `.zst`.
   Итого 1.2 ГБ мусора. Чинит шаг 2.

2. **Ежечасная ротация никогда не работала как задумано.** В
   `/etc/cron.hourly/logrotate-nginx-size` строка `#!/bin/sh` стоит **девятой**,
   после блока комментариев. Shebang действует только в первой строке.
   Файл отрабатывал лишь потому, что `run-parts` запускает его через `sh` —
   случайность, а не задумка. Именно поэтому `size 500M` не срабатывал и логи
   доросли до 779 МБ. Чинит шаг 3.

### Расхождение по диску: ~29 ГБ не найдено

Занято 50–51 ГБ из 59 (90%, свободно 6 ГБ), а при обходе файловой системы видно
только ~21 ГБ. Остальное почти наверняка в `/var/lib/docker` (права `drwx--x---`,
чтение недоступно без root).

**Действие:** после скрипта посмотреть `docker system df`. Крупное на диске:
`.git/objects/pack` 1.4 ГБ, `data/GmlBackend` 5.5 ГБ,
`data/GmlBackend/temp/JavaBuild/jdk-22` 132 МБ, `.pnpm-store` 125 МБ.
Также лежат два старых дампа БД: `data.db.backup` (29 МБ), `data.db.pre-hwidfix` (35 МБ).

### MySQL слушает 0.0.0.0:3306

Порт открыт на все интерфейсы. Проверить, закрыт ли он снаружи, не удалось —
`ufw` и `iptables` требуют root. **Проверить:** `sudo ufw status verbose`.
Если 3306 доступен из интернета — закрыть, оставив доступ только нужным хостам.

### SSH-брутфорс идёт активно

220 preauth-обрывов, `PermitRootLogin yes`. Топ-источник `117.187.180.166` (34 попытки),
далее `77.239.124.242` (10). fail2ban активен и работает. С перезагрузками
**не коррелирует** — это отдельная проблема, не причина зависаний.

### Порт 5003 не слушается

`gml-web-proxy` (порт 5003) не поднят — отсюда `ECONNREFUSED`. Слушается только 5004.
Вероятно, следствие краш-лупа `bots`; перепроверить после шага 5:
`docker compose ps` — все ли контейнеры Up.

## 5. ЧТО ДЕЛАТЬ ДАЛЬШЕ (по порядку)

1. **Запустить `deploy/fix-vds.sh` под root**, затем `sudo reboot`.
   Перед ребутом — проверить доступ к VNC-консоли хостера (см. раздел 3).

2. **После перезагрузки проверить, что первопричина устранена:**
   ```
   grep nomodeset /proc/cmdline                            # должен присутствовать
   journalctl -b -k | grep -c drm_fb_helper_damage_work    # ДОЛЖНО БЫТЬ 0
   docker compose ps                                       # все контейнеры Up
   docker logs --tail 50 polit-empire-bots-1               # без RuntimeError
   df -h /                                                 # должно освободиться ~1.4 ГБ
   ```
   Ключевой критерий успеха — **ноль** в счётчике `drm_fb_helper_damage_work`.
   Если там не ноль, `nomodeset` не подавил драйвер: проверить
   `lsmod | grep cirrus` и что блэклист применился.

3. **Показать `docker system df`** — решить, что чистить из ~29 ГБ.

4. **Проверить `sudo ufw status verbose`** — закрыт ли 3306 снаружи.

5. **Лаунчер — ВХОД ПОЧИНЕН (2026-07-27).** Симптом «лаунчер не логинит»
   оказался не багом кода: весь docker-стек, кроме `bots`, был остановлен.
   Сайт и `signin` отдавали 502. Лечение — `docker compose up -d` **без имени
   сервиса** (`up -d bots` поднимает только бота, а `restart: unless-stopped`
   не возвращает контейнеры, остановленные вручную, даже после ребута).

   Цепочка входа: лаунчер → nginx → `127.0.0.1:5004` (`deploy/gml-proxy.js`,
   node **на хосте**, не контейнер) → `127.0.0.1:5003` (`gml-web-proxy`) →
   `gml-web-api` → сайт `/api/gml/auth`. Прокси на 5004 живёт при лежащих
   контейнерах и сыплет `ECONNREFUSED 127.0.0.1:5003` — не путать со сбоем
   самого прокси.

   Быстрая проверка здоровья:
   ```
   ss -ltn | grep -E '3001|5003'
   curl -s -o /dev/null -w '%{http_code}\n' https://politempire.ru/api/news
   curl -s -X POST https://politempire.ru/api/v1/integrations/auth/signin \
     -H 'Content-Type: application/json' -H 'X-HWID: probe' \
     -d '{"Login":"x","Password":"x"}'
   ```
   Здоровый ответ signin — HTTP 400 с телом `statusCode: 401,
   "Неверный логин или пароль"`. Без заголовка `X-HWID` GML отвечает
   «Не удалось определить устройство» — это тоже норма, не поломка.

   Заодно исправлен реальный баг в `launcher/src-tauri/src/auth.rs`: перебор
   хостов GML прерывался на первом хосте, ответившем хоть чем-то на уровне TCP.
   При 502 резервный домен не пробовался, а сломанный хост закреплялся через
   `set_resolved_gml_host()` — и туда уходили все последующие запросы сессии
   (профиль, скачивание, authlib). Теперь ответ принимается только если он не
   5xx и тело — валидный JSON. **Не скомпилировано:** на сервере нет `cargo`,
   лаунчер собирается не здесь — проверить сборку при следующем билде.

6. **НЕ СДЕЛАНО: мод.** Владелец просил «исправлять мод с запросами», но
   конкретные симптомы не назвал — **нужно уточнить, что именно не работает.**
   Известный контекст:
   - В `data/GmlBackend/game data/PolitEmpire/mods/` изменены jar'ы:
     `pe_townymenu`, `pe_wars`, `politempire_hud`, `politempire_quests`, `politeshop`.
     Удалены: `CreativeCore_NEOFORGE_v2.13.36`, `pe_oilrig`.
   - Исходники мода — в `/opt/polit-empire/mod` (Gradle, NeoForge 1.21.1).
   - Незакоммичены также `plugin/src/main/java/ru/politempire/politeshopdc/`
     (`BalanceService.java`, `PoliteShopPlugin.java`).

7. **Место на диске: найдено, где лежат недостающие гигабайты.**
   `docker system df`: Build Cache 6.0 ГБ (5.1 ГБ reclaimable) + 1.21 ГБ в

   ```

   ```
   `docker system prune -a --volumes` **не запускать** — удалит образы и тома.

## 6. Важное про окружение

- Работать от `claudeuser`: **нет sudo, нет доступа к docker-сокету**.
  Всё под root запускает владелец вручную; в Claude Code — через префикс `!`.
- В репозитории много незакоммиченных изменений (см. `git status`), включая
  бинарники: `data.db`, jar-моды, png-скины. Коммитить только осознанно.
- Последний коммит на момент написания: `f8861bd8`
  («новый IP сервера 85.192.56.40 + не прятать сбой БД в /api/news»).
- Тестовый запуск бота из venv занимает порт 8180 — **не забыть погасить процесс**
  после проверки, иначе конфликт с контейнером.
